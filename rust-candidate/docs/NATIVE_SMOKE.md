# Hosted native UI smoke check

The repository-root Windows workflow builds the actual Tauri release executable with `src-tauri/tauri.smoke.conf.json`, then starts it on the hosted runner with a separate WebView2 data directory and a loopback Chrome DevTools Protocol port. [Playwright's WebView2 guide](https://playwright.dev/docs/webview2) documents this connection method. [Microsoft's elevated-host guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security#recommended-privilege-level-for-webview2-host-applications) explains why the earlier `WEBVIEW2_*` environment override may be ignored: the smoke configuration instead passes arguments through Tauri's WebView2 API. The normal `tauri.conf.json` contains no debug endpoint, and `tests/check_smoke_config.py` enforces that separation. `playwright-core` attaches to the app's existing WebView2 control; it does not launch a separate browser or serve mock frontend content.

`tests/make_smoke_fixture.py` generates a small, sanitized SQLite file with two invented matches, three rounds, two players and three utility events. `tests/native-smoke.cjs` enters that path through the visible app control and clicks **Open library**, which invokes the Tauri Rust commands. It checks match selection, overview, rounds, players, utility filtering and the second match, then confirms the fixture bytes did not change. It saves app-content PNGs for the overview, rounds and filtered utility tab, plus a JSON proof containing the fixture and screenshot hashes. All outputs are labeled **synthetic** and retained as short-lived GitHub Actions artifacts; no executable or private fixture is uploaded.

A passing build alone is not a native runtime or visual acceptance. The smoke job must launch, connect to WebView2, verify IPC-backed data and produce inspectable actual-window captures. These scripted observations still do not validate human usability, varied real imports, CS2/HLAE, editing, export or a packaged installer.

The first hosted native attempt, [run 39011503829](https://github.com/Gerbzz/DemoStrike/actions/runs/39011503829), compiled the release executable and generated the fixture, but the WebView2 CDP endpoint did not open within 60 seconds. [Run 39012443035](https://github.com/Gerbzz/DemoStrike/actions/runs/39012443035) confirmed that the application had a responding native window and WebView2 processes in the same desktop session; its environment-variable debug flag still did not open the port. Neither run produced a screenshot or IPC proof. The CI-only configuration addresses that specific diagnostic; its result must be verified before claiming native runtime or visual acceptance. A failed or unavailable native session must not be represented by a browser-rendered frontend image.
